Legacy kod, her yazılımcının er ya da geç yüzleştiği bir gerçek. Peki bu labirentin içinde nasıl kaybolunmaz?

Teknik Makale · Nisan 2026 · ~8 dk okuma

Bu makaleyi ne tam anlamıyla uyguladığım için ne de teorik bilgimi paylaşmak için yazdım. Altı yıldır embedded yazılım geliştiriyorum ve hâlâ devraldığım sistemlerin önünde ne yapacağımı bilemediğim anlar oluyor.

Son deneyimim şöyle: Bir kart üzerinde çalışan en az 4 farklı firmware versiyonu vardı. İçlerinde açık TODO ve FIXME yorumları var — neden kapanmamış, kim yazmış, ne zaman, hiçbir izi yok. İlk baktığımda hem "hallederim" dedim hem de "nasıl olacak" diye dertlendim. İkisi aynı anda.

Bu ikili his sanırım bu işin içinde olan herkesin tanıdığı bir his. O yüzden hem kendim için bir referans oluşturmak hem de benzer durumda olanlara bir şeyler katabilmek için internetteki kaynaklardan da faydalanarak bu dokümanı yazdım.

Reddit'te bir yazılımcı şöyle yazmıştı: "Sıfır dokümantasyonlu, bir iş arkadaşından devralacağım bir .NET Core + Knockout.js projesi var. Nereden başlayacağımı bilmiyorum." Bu his evrensel. Hangi dili, hangi platformu, hangi sektörü kullansanız — bir gün birinin bıraktığı sistemi devralmak zorunda kalırsınız.

Embedded sistemlerde bu durum özellikle ağır hissettiriyor. Belgesiz register konfigürasyonları, magic number'larla dolu interrupt handler'lar, kimsenin dokunmaya cesaret edemediği clock tree ayarları. Ve en kötüsü: "çalışıyor, dokunma" kültürü.

Aşama 01

Triage — Sistemi Tanı, Dokunma

Deneyimli yazılımcıların hemen hemen hepsi aynı ilk tavsiyede hemfikir: ilk hafta hiçbir şeyi değiştirme. Orta-büyük ölçekli bir legacy codebase'i gerçekten tanımak 6 ila 12 ay alır. Hemen "şunu düzelteceğim" refleksiyle başlamak, genellikle felakete davet çıkarmaktır.

"Legacy sistemler temizlenmiş bir sızdıran boru gibidir. Kirliliği giderdiğin an fışkırır. Küçük bir bug'ı düzeltirsin, aniden tüm kapaklar açılır."

— Erik Dietrich, DaedTech

İlk hafta şunlara odaklan:

  • En sık değişen dosyaları tespit et: git log --stat
  • Magic number'ları ve açıklamasız sabitleri listele
  • "Dokunma çalışıyor" yorumlarını işaretle
  • Dead code bloklarını not et
  • Static analiz aracı çalıştır: cppcheck, PC-lint
// Bir legacy codebase'de karşılaşılan tipik code smell'ler (sorunlu kodun uyarı işaretleri)

// 1. Global değişken cehennemi
volatile uint32_t g_flag1, g_flag2, g_flag_bak, g_flag_bak2;

// 2. Magic number
if (status == 0x3F) { ... }  // Ne anlama geliyor?

// 3. "Dokunma çalışıyor" yorumu
// HAL_Delay(50); // BU OLMADAN ÇALIŞMIYOR - NEDENİNİ BİLMİYORUM

Bu haritayı çıkarmadan müdahale etmek, gözü bağlı ameliyat yapmak gibidir.

Aşama 02

Güvenlik Ağı — Önce Test, Sonra Değişiklik

Michael Feathers, Working Effectively with Legacy Code kitabında "seam" (dikiş noktası) kavramını tanımlar: kodda test ekleyebileceğin, müdahale edebileceğin izole noktalar. Legacy kod çoğunlukla unit test içermediğinden, değişiklik yaparken kör uçuyorsunuzdur.

Embedded bare-metal projelerde resmi bir test framework'ü genellikle olmaz. Ama bu, test yazılamaz anlamına gelmiyor. Donanımdan bağımsız saf fonksiyonlar için en basit yöntem bile işe yarar. Pratik yaklaşım:

  1. Donanımdan bağımsız, saf fonksiyonları tespit et (CRC, protokol parsing, buffer mantığı)
  2. HAL bağımlılıklarını mock'la
  3. Her dokunduğun fonksiyona önce test yaz, sonra değiştir
// Framework gerekmez — saf fonksiyonları printf ile test et

void test_modbus_crc(void) {
    uint8_t frame[] = {0x01, 0x03, 0x00, 0x00, 0x00, 0x02};
    uint16_t result = calculate_crc(frame, 6);
    if (result != 0xC40B)
        printf("FAIL: CRC beklenen=0xC40B, gelen=0x%04X\n", result);
    else
        printf("PASS: CRC\n");
}

// Donanıma bağımlı kısımları koşullu derlemeyle izole et
#ifdef UNIT_TEST
    uint16_t mock_adc_read(void) { return 2048; }
    #define ADC_Read() mock_adc_read()
#endif

Bu altın kural pratikte çok işe yarıyor. Kısa vadede yavaşlatıyor gibi görünse de, test olmadan yapılan "hızlı" düzeltmeler çoğu zaman üç kat iş çıkarıyor.

Aşama 03

Strangler Fig Pattern — Boğmadan Değiştir

Martin Fowler'ın tanımladığı bu pattern, eski sistemi bir anda yeniden yazmak yerine yeni kodu yanına yerleştirerek yavaş yavaş ikame etmeyi öngörür — tıpkı bir sarmaşığın ağacı yavaşça sarması gibi. Embedded'da bunu zaten farkında olmadan yapıyoruz: eski fonksiyonu silmeden yanına yenisini yazıp #ifdef ile geçiş kontrolü yapmak aslında tam olarak bu. 

// ESKİ KOD — henüz dokunma
void old_uart_handler(void) {
    // 200 satır spagetti mantığı...
}

// YENİ KOD — temiz, test edilmiş
void new_uart_handler(void) {
    // Yeniden yazılmış, izole edilmiş versiyon
}

// KÖPRÜ — geçiş döneminde ikisini birden taşı
void uart_handler(void) {
#ifdef USE_NEW_UART
    new_uart_handler();
#else
    old_uart_handler();
#endif
}

Refactoring ile fonksiyonel değişikliği asla aynı commit'te karıştırma. İkisi birden gittiğinde ne code review yapılabilir, ne de hata tespiti kolaylaşır.

Aşama 04

Hotspot Analizi — Doğru Şeyi Düzelt

cppcheck ya da PC-lint çalıştırdığında yüzlerce uyarı döner. Hepsini düzeltmeye çalışmak ne mümkün ne de anlamlı — bazı dosyalara yıllardır kimse dokunmamıştır, dokunmayacaktır da. Öncelik formülü:

Karmaşıklık + Değişim sıklığı = Hotspot. Hiç dokunulmayan karmaşık kod önemsizdir. Sık değiştirilen basit kod ise kritiktir.

— Nicolas Carlo, understandlegacycode.com

Teknik borç (technical debt) — hızlı çözüm uğruna ertelenen düzeltmelerin birikimi. Bunu önceliğe göre sırala:

Kritik
Stack overflow riski, ISR'da malloc, buffer overflow
→ Hemen
Önemli
Magic number'lar, paylaşılan global state
→ Sprint'e al
İyileştirme
Kötü isimlendirme, dead code blokları
→ Zamanla
Kozmetik
Formatting, yorum dili tutarsızlığı
→ Otomasyona
Aşama 05

ADR — Sonraki Geliştiriciyi Kurtar

Teknik kararlarını belgele. Architecture Decision Record (ADR) formatı bunun için idealdir: kısa, net, aranabilir. docs/adr/ klasörüne kaynak kod yanına koy.

## ADR-001: uart_init içindeki HAL_Delay(50)

Tarih: 2026-04-07
Durum: Aktif

Bağlam:
  UART init sonrası delay kaldırılınca slave cihaz
  ilk Modbus frame'ini kaçırıyor.

Karar:
  Delay bırakıldı. Kök neden: RS-485 transceiver
  DE/RE pin geçiş süresi + slave bootloader gecikmesi.

Sonuç:
  Donanım revizyonunda pull-down hızlandırılırsa
  kaldırılabilir.

10 ADR, 1000 satır yorumdan değerlidir.

Yeni başladığında sistemin garip davranışlarını, çözdüğün hataları, "a-ha!" anlarını not et. Ham Markdown notlar bile olsa, bunları kaynak kod yanında tutmak sonraki geliştiriciyi kurtarır.

Sonuç

Kültür Problemi Teknik Çözüm İster

"Çalışıyor, dokunma" kültürü her sektörde, her dilde var. Bunu kırmak için değişikliği görünür, izlenebilir ve geri alınabilir yapmak gerekiyor. Conditional compilation, anlamlı commit mesajları, version tag'leri ve kısa ADR dosyaları bunun temelidir.

Bir de şunu söyleyeyim: bu işin bir "ödülü" de var. Onca versiyon arasında hangisinin doğru olduğunu bulmak, o sessiz panikle başlayıp yavaş yavaş sistemi anlamlandırmak — sonunda bir yere varıldığında hissettirdiği şeyi başka bir şeyle karşılaştıramıyorum.
